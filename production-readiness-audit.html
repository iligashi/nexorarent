Production Readiness Audit

Repository: iligashi/nexorarent
Date: 2026-10-27
Overall verdict: This is a strong MVP / beta application. It is not fully production-ready for public launch yet, but it is close enough to be a serious private beta or pilot deployment if the critical hardening items are addressed.

Executive Summary

The repository has a sensible architecture: a TypeScript-heavy Next.js frontend and a Node/Express backend with MySQL support. The project is organized, modern, and clearly built as a real product rather than a toy app. It includes strong foundations such as Helmet, CORS, rate limiting, JWT-based auth, bcrypt password hashing, and structured backend routing.

However, production readiness is not achieved yet. The largest gaps are around authorization enforcement, testing, deployment pipeline, secret management, monitoring, and backup strategy. This app is much closer to a beta / pilot application than a hardened production system.

Priority Checklist

P0 - Must Do Before Public Production

  • Add environment validation at startup for secrets and required DB settings.
  • Verify all admin routes enforce role-based authorization, not just authentication.
  • Harden refresh token cookie settings for production HTTPS use.
  • Add upload validation for file type, file size, malicious names, and path traversal.
  • Set up CI/CD with lint + build + tests + dependency audit.
  • Introduce automated test coverage for auth, booking, admin, and reservation edge cases.
  • Define backup/restore and rollback strategy for the database.
  • Set up monitoring and alerting for errors, latency, and DB health.

P1 - Strongly Recommended Before Launch

  • Deploy to managed production infrastructure instead of local XAMPP-style setup.
  • Use structured logging with request IDs and user IDs.
  • Review all admin actions for audit logging.
  • Add per-route rate limits and abuse protections.
  • Validate all request payloads and enforce request-size limits.
  • Review email sending, retries, and failure behavior.
  • Implement graceful degradation for DB or email system outages.

P2 - Good to Have Soon After Launch

  • Feature flags.
  • Cache strategy for public listings and landing pages.
  • Performance profiling.
  • Business analytics and funnel tracking.
  • Data retention policy and privacy controls.

Security Audit

Authentication

Good: bcryptjs is used for password hashing, JWT is used for access/refresh tokens, and queries are parameterized.
  • Passwords are hashed with bcrypt before storage.
  • JWT access tokens and refresh tokens are issued with expiration times.
  • Auth routes validate input schema using Zod.
Risks: refresh token cookie settings are not fully hardened for production, and there is no clear evidence of a dedicated admin authorization middleware by route.
  • Cookie strategy needs careful tuning for HTTPS and cross-site conditions.
  • Admin access must be enforced by middleware and not assumed by URL structure.
  • Threat models for brute force and account takeover should be reviewed and tuned.

Authorization

This is the most important verification area before launch. The repository includes numerous admin routes and dashboard-specific APIs; those must enforce role-based authorization strictly.
  • Confirm only admins can access admin dashboards and revenue/booking management APIs.
  • Protect pricing, reservations, customer data, and loyalty management endpoints.
  • Ensure admin actions are logged and auditable.

Database Layer

  • Parameterization is used in the auth routes, which is a good sign.
  • There are migration and seed scripts, which helps local setup and deployment consistency.
Risks: local XAMPP assumptions are fine for development but not production, and there is no visible backup or rollback strategy.
  • Move to managed MySQL or PostgreSQL for production.
  • Use automated backups and DB monitoring.
  • Add migration rollback procedures.

Upload and Media Handling

File upload routes are a common production risk if not tightly controlled.
  • Whitelist allowed file types.
  • Set file-size limits.
  • Prevent path traversal and malicious filenames.
  • Scan uploaded media if it is user-supplied.

API Security

Good: Helmet, CORS, rate limiting, JSON parsing, and a 404 handler are all present.
  • Security headers are enabled with Helmet.
  • CORS is configured.
  • Application-level rate limiting is in place.
Risks: there is no visible proof of production-grade request validation for all endpoints, no clear secrets-validation startup check, and no visible monitoring pipeline.

Deployment Recommendations

Frontend

  • Deploy client/ to Vercel or Netlify for a production-grade Next.js setup.
  • Use environment variables for public API URLs and site config.

Backend

  • Deploy server/ to Railway, Render, Fly.io, DigitalOcean App Platform, or a similar managed Node runtime.
  • Use managed MySQL or PostgreSQL instead of local XAMPP.

Database

  • Use managed DB with automated backups and DB health monitoring.
  • Separate staging and production environments.

CI/CD

  • Run lint, build, tests, and dependency audit on every push.
  • Block deployment if checks fail.

Monitoring

  • Add Sentry for frontend/backend error tracking.
  • Set uptime checks and DB health checks.
  • Aggregate logs and inspect request error trends.

Launch Plan

  1. Hardening sprint: env validation, role checks, upload validation, monitoring, backup plan.
  2. Staging deployment: production-like config and real DB.
  3. Private beta: pilot with a limited audience.
  4. Production launch: after stable metrics and rollback process are proven.

Final Verdict

MVP / Beta: 70/100
Production-ready: 45–55/100

This project is a strong beta application with good architectural foundations. It is not yet production-ready for a public launch, but it is near enough to become a credible private beta or pilot deployment with a focused hardening sprint.
